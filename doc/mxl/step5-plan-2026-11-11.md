## 1. What Step 5 delivers

Today one Nandi process decodes, mixes, adds graphics, **and** encodes every output. Step 5 moves encoding out:

```
                         MXL domain (tmpfs, /run/mxl)
 ┌──────────── Nandi (main) ───────────┐         ┌──────── Worker 1 (Nandi, MXL input) ──────┐
 │ inputs → decode → compose/graphics  │  video  │ mxlsrc ×3 → outputs moved from main:      │
 │ SCTE timeline (scheduler, ESAM,     ├────────►│   encode → mux (SCTE PID) → SRT/UDP/HLS   │
 │ POIS, blanking) → programme output  │  audio  └───────────────────────────────────────────┘
 │   type "mxl": video + audio + data  ├────────►┌──────── Worker 2 … ────────────────────────┐
 │ (outputs that stay in-process)      │  data   │ same, other outputs                        │
 └─────────────────────────────────────┘ (SCTE)  └───────────────────────────────────────────┘
```

Gains expected (not yet measured): an encoder can crash, be restarted or be replaced without touching the channel; several encoders or
other programs read one decoded programme; encoding can later move to another host (Step 6, Fabrics; skipped on 2026-11-24).

## 3. Work packages in detail

### WP3: the worker

**Recommended worker: a second Nandi engine with an MXL input**, rather than a `gst-launch-1.0` pipeline.

| | Nandi as worker | `gst-launch-1.0` |
| --- | --- | --- |
| Outputs supported | All of them (SRT, UDP, RTMP, HLS, DASH, file, S3), with Nandi's encoder settings, SCTE PID, null interval, HLS cue tags and DASH events | Whatever the hand-written pipeline has. SCTE, HLS cues and DASH events would need writing again. |
| SCTE | Arrives through the existing `onScteData` path (WP2), so all output logic is reused | Needs its own code |
| Control | Same REST/gRPC/UI; a worker is just a channel | None |
| Cost | One extra engine process. Measured MXL input channel: 0.25 core at 720p25 and 0.59 core at 1080p25, encoding included | Slightly less |
| Status | MXL input built and tested (Step 4) | Not built |

Tasks:
1. **Config split.** A channel's outputs are divided between main and workers. Main gets one `outputs[n].type = "mxl"` output. Each worker is a
   channel whose `inputs[0].transport.uri = "mxl:///run/mxl"` with the three flow IDs (video, audio, data), plus the moved outputs. No
   new config type; both halves use what exists.
2. **Compose.** Add a `transcoder-worker` service from `utpl/transcoder:mxl`. It mounts the `mxl-domain` volume **read-only**, has its own
   `config/worker-*.json` (top-level `config/`, per AGENTS.md) and `restart: unless-stopped`. With no orchestrator, Docker restarts it.
3. **Health.** The worker reports input state (frames, late buffers, reattach count) through the stats it already has. Its existing
   3 s no-data timeout and 900 ms retry handle a restarted main.
4. **Keyframes at splice points.** In-process, Nandi asks the encoder for a keyframe at each splice point (the `running-time-map` in
   `Scte35Data`). The worker must do the same from the cue it receives. WP2 delivers the cue early enough (the pre-roll) for this.

Done when: a 1080p25 channel split into main plus one worker produces the same streams (`ffprobe`, TSDuck) as the in-process channel. Its
lip-sync, drops, latency and CPU meet Gate A.

**Status (2026-11-12): built and measured in a scratch build; one Gate A limit (CPU) is not met, lip-sync is met with little room.** **Update 2026-11-25:** on the installed images the CPU limit was met in all runs at 1080p25 and missed in one of five at 720p25 ([page 41](../codebase/41-mxl-integration.md#step-5-on-the-installed-images-2026-11-24-and-25)). Config split and Compose service done (`config/mxl_split_*.json`, service `transcoder-worker`); the health is the engine's own log lines plus `GET /mxl/flows`. Differences from the tasks above, each found by measuring:

- **An engine change was needed.** A channel whose outputs are all MXL lost more than half of its pictures with a UDP or RTMP input (the three-second input buffer is drained only by a clock-paced output). It now takes the input without that buffer (`engine.cpp`).
- **Keyframes at splice points (task 4): not met, and not a worker problem.** The in-process output has no keyframe at a splice either (0 of 9, scene cut off, key interval 10 s). Why the muxer's request has no effect is unknown.
- **Gate A at 1080p25:** same streams, frame rate and events; **lip-sync** first 55 to 70 ms from in process, then, after two fixes (video put on MXL's grain grid; the sound's wait counted from its first buffer), -34 to +23 ms in five clean runs against a limit of 40 ms; **CPU 1.35 to 1.39 times** (limit 1.25 times, not met).

Details and the other numbers: [41, The worker](../codebase/41-mxl-integration.md#the-worker-a-channel-split-in-two-step-5-wp3); log entries 20 to 24 in [step5-change-log.md](step5-change-log.md).

### WP4: flow registry

The minimum a registry must do, using only MXL v1.1.0 and files:

| Need | How |
| --- | --- |
| Stable flow UUIDs across restarts | Already true: flow IDs are in the channel config. Add a check at config load that no two outputs or channels use one ID. |
| One writer per flow | Before creating a writer, `mxlIsFlowActive` (shared advisory lock on the flow's data file). If another process is active on that flow: refuse, log, and fail open, as `MxlTap` already does. |
| Stale-flow cleanup | `mxlGarbageCollectFlows` (removes flows with no active lock) once at engine start and every 60 s. `mxl-info -g` by hand. |
| Listing | `GET /mxl/flows` in the API. It reads each flow's descriptor JSON from the domain mounted read-only, so the API image needs no MXL SDK. It returns ID, label, format, grain rate, writer active, and the group-hint tag `<channel>:<output>`. |
| Discovery by name | NMOS group-hint tags on every flow (`urn:x-nmos:tag:grouphint/v1.0`, as `flow.h` recommends), so a worker config can name a channel and an output instead of three UUIDs. Optional in Step 5. |

**Status (2026-11-11): built, in a scratch build.** Differences from the table above, each found by reading the MXL v1.1.0 source or measuring:

- **Stale-flow cleanup runs once at start, not every 60 s.** The `mxlsink` and `mxlsrc` elements already run `mxlGarbageCollectFlows` when they initialise, so a timer adds nothing; and MXL's active test and cleanup take an exclusive lock for an instant, which a timer would repeat for nothing.
- **The one-writer check is at tap creation only.** It refuses a flow a writer in another process holds. It does not notice a writer that appears later. Config load also refuses two writers on one flow, and a flow the same channel writes and reads.
- **`GET /mxl/flows` reads the domain where the API runs** (the engine's container in the Compose stack) and detects a live writer from `/proc/locks`, not by taking MXL's lock, so polling cannot disturb a writer.
- **Group-hint tags are set by the plugin**, not by Nandi, so discovery by channel and output name is not built.
- **libmxl is loaded with `dlopen`**, so the engine needs no SDK at build or run time.

Where: [41, Flow registry](../codebase/41-mxl-integration.md#flow-registry-step-5-wp4); log entries 07 to 11 in [step5-change-log.md](step5-change-log.md).

Not in Step 5: an NMOS IS-04 registry. MXL is NMOS-shaped, so this is the natural later step if several vendors' programs must find
Nandi's flows.

## 4. SCTE-35 markers over MXL: everything that exists, and what we can build

### 4.1 Short answer

- **Yes, SCTE markers can travel inside MXL today, without a side channel.** MXL v1.1.0, which is already in our images, has **data
  flows** (`MXL_DATA_FORMAT_DATA`, `media_type: "video/smpte291"`). A data flow carries SMPTE ST 291 ancillary-data (ANC) packets,
  one 4096-byte grain per video frame. It shares the video's grain index, so a packet is tied to an exact picture.
- The standard way to carry an ad cue in ANC is **SCTE-104**, placed in ANC by **SMPTE ST 2010** (DID 0x41, SDID 0x07). This is how SDI and
  ST 2110-40 plants carry SCTE today, and an encoder turns SCTE-104 into SCTE-35. The GStreamer MXL plugin already reads and writes data
  flows: `mxlsink`/`mxlsrc` accept `meta/x-st-2038` and have a `data-flow-id` property. **Checked in our image on 2026-11-11.**
- **Upstream MXL `main` (unreleased, 1.2.0-dev) added *event flows*** on 2026-10-13: a timed queue of variable-size events, each with a
  TAI timestamp and a Data Item Type. They are designed for bit-exact **SMPTE ST 2110-41** (Fast Metadata) round trips. This is the
  closest thing to a native SCTE-35 carrier, but it is **not released** and the GStreamer plugin does not support it yet.
- **No standard identifier for SCTE-35 exists** in either place yet. The ST 2110-41 Data Item Type register (checked 2026-11-11) lists
  only ST 2127-2 metadata, IPMX/VSF entries and two private SiriusXM entries, one of them "SCTE104 JSON". MXL's own URN-based DIT scheme
  is marked "TODO" in its docs. **This is the gap we can fill** (section 4.7).

### 4.2 What Nandi has to carry

Nandi works with whole SCTE-35 `splice_info_section`s (`Scte35Data`: a `GstMpegtsSection`, its running time and a running-time map for
keyframes). The base64 path promises that **every byte the operator supplied reaches the wire**: only `pts_adjustment` and the CRC are
changed (page 16). Any carrier that loses bytes breaks that promise for Nandi-to-Nandi hops. This is the main test for each option below.

The MXL output already has an empty hook, `MxlOutput::putScteData` (`output/mxl.cpp:109`), which receives exactly what the TS muxer
receives. On the reading side, the MXL input can raise the same `_scteDataCallback` that the TS demuxer path raises (`input/single.cpp:1517`).
Everything downstream (muxer SCTE PID, HLS cue tags, DASH events, blackout, ad switching) would then work unchanged.

Notes on the evidence:
- Data flows, `mxl-data-probe`, and video/data synchronisation tests (same absolute grain index on both flows) are in v1.1.0 (released
  2026-09-09). Event flows are in `main` only (commits from 2026-10-13 onward). An open upstream issue (#798, 2026-10-27) proposes changing
  their flow descriptor, so the format is **not stable yet**.
- A data-flow grain is 4096 bytes and holds at most 255 ANC packets (upstream issue #496). One packet holds 255 user data words. A typical
  SCTE-104 message or SCTE-35 section (under 300 bytes) is one or two packets, so this is not a limit for cues.
- The ST 2038 elements of gst-plugins-rs (`st2038extractor`, `st2038combiner`) are **not in our image**. They are not needed: Nandi can
  write and read the ANC bytes itself through `appsrc`/`appsink` into `mxlsink`/`mxlsrc`.
- Open-source code for SCTE-104 exists: **libklvanc** (VANC parse and build, including SCTE-104) and **libklscte35** (SCTE-104 ⇄ SCTE-35),
  both LGPL-2.1 and active in 2026. They are used with FFmpeg's DeckLink input. For SCTE-35 parsing: Comcast `scte35-go` (Apache-2.0)
  and `threefive` (Python, MIT) are useful as test oracles. GStreamer's own `GstMpegtsSCTESIT` (already used by Nandi) can build the
  SCTE-35 section on the reading side.

### 4.4 Recommendation

**Owner direction, 2026-11-11: SCTE-104 is not a priority.** Step 5 therefore ships option **B** only.

1. **Step 5 ships option B on MXL v1.1.0.** One data flow per programme output carries the **unchanged SCTE-35 section** in a private ANC
   packet, in the grain of the cue's picture. This is lossless with no conversion and no third-party library. Only Nandi readers understand it.
2. **SCTE-104 (option A) is deferred.** Add it later behind the same carrier interface if a third-party reader or writer needs it.
3. **Prepare option C behind the same interface.** Writer and reader each go through one small `ScteCarrier` class. When MXL releases
   event flows (expected in 1.2.0) and the descriptor issue #798 is settled, add an event-flow carrier. Choose per output by config,
   with no change elsewhere.
4. **Propose the missing identifier upstream (option D)**, after owner approval (outward-facing; same rules as the `mxlsrc` report):
   - an MXL issue proposing standard MXL DITs for "SCTE-35 splice_info_section" and "SCTE-104 message";
   - event-flow support in `gst-mxl-rs`, as a PR, if we write it anyway;
   - an ST 2110-41 DIT registration later, ideally through SCTE so that it becomes a standard rather than a company entry.

### 4.5 How timing works (option B)

- **Writer (main).** `putScteData` receives the section and its running time. Its splice time (the running time of the splice point) is
  turned into the MXL grain index with the **same** running-time-to-TAI mapping `mxlsink` uses for the video flow. That gives
  `spliceGrain`.
- **Pre-roll.** The cue is written into the grain of the picture going out now. The section is copied as is, and the private packet adds
  a small header with `spliceGrain`, so the reader does not need the writer's PTS base.
- **Repetition.** The ring holds only 5 frames at 25 fps (about 200 ms). A worker that is restarting or late would miss a cue written
  once. So the writer **repeats the cue in every grain from the moment it is known until the splice grain** (with the pre-roll counting
  down), and once more at the splice grain. The reader keeps the first copy and drops repeats by `splice_event_id` (or
  `segmentation_event_id`). SCTE receivers already dedupe this way.
- **Reader (worker).** Reading ANC uses the same timeline shift as video (`delayMs`), so the splice grain maps to the worker's own
  running time. That becomes `Scte35Data` (section with `pts_adjustment` re-based by the existing `sectionFromBase64` logic, running time,
  running-time map) and goes to `_scteDataCallback`. From there it is the in-process path.
- **Immediate splices** (`splice_immediate_flag`) carry pre-roll 0 and take effect on the grain that carries them, as in-process.

### 4.6 WP1: the spike (about 1 day, can start before the decisions)

The spike lives in `../experiments/scte-over-mxl/`, not in the product tree, so it needs no decision. With SCTE-104 deferred, only
frame alignment is left to prove:

1. Write a raw-section packet into a v1.1.0 data flow with `mxlsink` (ST 2038 bytes from `appsrc`) next to a video flow. Read both back
   with `mxlsrc` and `mxl-data-probe`. Check, for 100 cues, that each lands on the intended video grain index and comes back byte-identical.
2. Check that a separate `mxlsink` for data in Nandi's side pipeline uses the same grain index as the video `mxlsink`. The shared offset
   was fixed upstream in July 2026; confirm it in v1.1.0 with our `MxlFrameGrid`.

Output: a one-page result. If the indices disagree, the data must be written through the C API from the same `MxlFrameGrid` (section 6).

**Result (run 2026-11-11, tool and logs in `../experiments/scte-over-mxl/`; details in [step5-change-log.md](step5-change-log.md)).**
The trial proved the carrier and found three rules that WP2 must follow:

| # | Finding | Evidence | Rule for WP2 |
| --- | --- | --- | --- |
| 1 | Sections come back byte-exact and on the right frame when video and data are written from **one pipeline** | 0 misaligned grains in about 1,400 grains with cues, including 54 runs scanned at the worst timing in a slot (±300 µs) | Write video, audio and the cue flow from the **same side pipeline** |
| 2 | With **one pipeline per flow** (how the source tap is built today) a cue can land **one frame late for the whole run** | 2 of 4 runs misaligned at +2 µs from the half-slot point, all 44 cue grains one frame late; other offsets fine | Do not give the data flow its own pipeline. If that cannot be avoided, stamp the data with the video frame's own time and check the first cue after every start |
| 3 | A **sparse** data flow (grains written only when there is a cue) lets a late reader be handed a **stale grain from an earlier lap of the ring** for an index that was never written | Late reads returned a cue written 4 or more frames earlier (8 of 48 and 4 of 23 cue grains) | **Write a data grain for every video frame**, empty when there is no cue (an empty grain is valid and read back as empty; 0 stale reads when written every frame, a late reader gets a clean "too late" instead) |

Further results: a reader that joins 1, 2 or 3 s late still catches every cue whose window it overlaps (repeating the cue in every grain
from the time it is known until its splice frame works; at least 7 frames of warning in the worst case here); two or three cues in one
grain were read back byte-exact (37 cues, 273 grains); sections of 28 to 2800 bytes work, and **a grain holds at most 4096 bytes in total
(about 2800 bytes of section in one grain, less when cues overlap)**; a 3000-byte section made the data sink stop writing for the rest of the
run (no data from the failure on). The writer must therefore check the size before writing and drop an oversize cue with a log line, never
reach the sink. Placeholder DID/SDID were used; a real private value is still to be chosen.

**Status of WP2 (2026-11-12): built and tested in a scratch build** (page 41, "SCTE-35 over MXL"; change log entries 14 to 19). Differences from the table above:

- The library is `mxlcarrier.{h,cpp}` in `utpl/transcoder/` (not `transcoder/scte/`), with `CueQueue` for the writer and `Deduper` for the reader.
- Each copy of a cue carries a **countdown in frames** to the splice, not an absolute splice frame (the writer does not know the grain index). A repeat is recognised by the section's bytes within 1.5 s, not by event id.
- The output has `mxl.data.flowId`, not a third stream of type `data`; the input has `transport.mxl.data.flowId`. Both are optional and need their own flow id.
- The reader is a probe on the data flow's own `mxlsrc` (it joins the input's reattach watch, not its learning of the shift); it takes cues once the shift is known.
- **Found: a GStreamer `mpegtsmux` bug** (it ORs bit 32 of `pts_adjustment` and never clears it), which put splices 13 hours away when a cue was re-based earlier than its authored time. The reader sets the authored time to 0 first (`withSpliceTimeZeroed`). Page 27.
- **Gate A, SCTE row:** "every cue on the same frame as the in-process output" was measured against where the **source** put the cue, because the in-process output itself is off by 22 to 208 ms and drifts on a source with a different clock. Through MXL the cues are within 37 ms (under one frame) of the source's placement. The owner approved the rewording on 2026-11-12: the limit is now "within ±1 frame of the splice time the source authored", and the in-process drift is a known gap (page 27).
- SCTE-104 is still deferred; the DID/SDID are still placeholders.

## 6. Risks

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Third-party programs cannot read Nandi's cues (SCTE-104 deferred) | Only Nandi workers get SCTE | Accepted for Step 5; add option A behind the carrier interface when needed |
| The data `mxlsink` and video `mxlsink` disagree on grain index | Cues one frame off for a whole run. **Seen in the trial** with one pipeline per flow (2 of 4 runs at one timing) | Same side pipeline for video and data (section 4.6, rule 1 and 2); fall back to writing data through the C API from the same `MxlFrameGrid` |
| Event-flow format changes upstream (#798) | Rework for option C | C stays behind the carrier interface and waits for a release |
| A ring of 5 frames is shorter than a worker restart | A cue written once is missed | Repeat until the splice grain (4.5) |
| Keyframe at splice point missing on the worker | Splice not on an IDR | Pre-roll lets the worker request it; S1 checks the IDR |
| CPU of main plus worker over Gate A | Splitting costs more than it saves | Measure in WP7; the programme tap costs about 0.1 core at 720p25 and the 1080p cost is not measured yet |
| Outward-facing upstream work | Policy | Owner approval and the employer's open-source policy before anything is posted |
